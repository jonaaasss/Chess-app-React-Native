# Chess Opening Flashcards — Project Context & Instructions

## What this app is

A React Native / Expo app for studying chess opening repertoires as flashcards. The user (Jonas) builds a personal repertoire per color (White/Black), organized as **Repertoires → Openings → Cards**. Each card has one of three modes with very different study behavior (see Data model below). This is a personal project under active, iterative development — not yet shipped publicly.

## Data model (src/types.ts)

- `Repertoire` (per `GroupId`: `'white' | 'black'`) → `Opening` → `Card`.
- `Card.mode: 'reactions' | 'others' | 'plan'`. All three share `Card.boards: ReactionBoard[]` (up to 6 boards per card, 2-column grid, always **at least 1** — a card has no text/state of its own anymore, so it can't be boardless). Mode toggle order in the editor is Reactions, Plan, Others.
  - **Study text lives on each board, not the card** — a single "Description" field in the board editor, always labeled the same regardless of mode. What it's actually bound to varies: for Reactions it's always `board.front.text` (shown throughout Study); for Plan always `board.back.text` (shown alongside the plan); for Others it follows the Flip button (`activeFace.text`, i.e. `board.front.text` or `board.back.text` depending on which side you're currently viewing) — the editor just reads/writes `board[side].text`, since `side` is already permanently `'front'` for Reactions and `'back'` for Plan, so no per-mode branching is needed in that one TextInput. `descriptionFace()` in `CardEditorOverlay.tsx` carries a board's description over to the right face when its *mode* changes (Reactions↔Others↔Plan), so it's never stranded on a face the new mode doesn't show.
  - **Reactions**: one continuous, rules-accurate chess game recorded via a real chess engine (`chessEngine.ts` — full legality, check, castling, en passant, promotion, SAN). You set up a position, press Play, then play out moves which get recorded into a branching tree (`MoveNode`, PGN-like — `children[0]` is the main line, further children are variations created by rewinding and playing a different move). In Study, the app auto-plays the opponent's side; you must find your own moves; branches show a numbered-arrow walkthrough of every recorded option before continuing. Uses `ReactionBoard`'s top-level `pieces/turn/castling/enPassant/arrows/circles/recording` fields — **no front/back position split** (`back` is unused; `front` only for its `.text`).
  - **Others**: a free-form annotated position (also built via the real chess engine now, forced legal move order — no longer the old simplified/no-turn-order editor). `front` and `back` (`BoardFace`: `pieces/turn/castling/enPassant/arrows/circles/text/moves`) are **fully independent** — different position AND different annotations (and text) allowed. This is the only mode with an editor Flip button/side label. An "Apply to Back" button in the editor copies front's position/arrows/circles/moves → back as a one-off convenience (back's own text is left alone); nothing keeps them in sync automatically.
  - **Plan**: there is **no front/back split** — one position, one set of arrows, one description, all living on `back` (`front` just mirrors `back`'s position/moves in the background and is otherwise unused/never shown; no Flip button, no hidden bare view — you draw the plan's arrows directly on the position you're building). The board can't be saved with **zero arrows** (validated in the editor's Save handler; blocked with a dialog suggesting "Others" as the alternative if you don't want to use arrows). In Study, the position is shown bare (arrows/circles hidden) and you must **draw the arrows yourself** directly on the board (drag gesture). Colors are auto-assigned in a fixed cycle — green → orange → red → blue — skipping colors that weren't used, repeating a color as many times as it was used before advancing. Each drawn arrow is validated immediately (wrong → flashes and reverts, counts as a mistake, matching the "wrong move" pattern from Reactions); order *within* a same-color group doesn't matter. Circles are revealed only once the board is fully solved (decorative, not validated).
  - **Others/Plan move history**: each `BoardFace.moves: BoardMove[]` is a permanent, linear (non-branching) record of the moves that built its position — survives closing/reopening the editor and duplicating the board, unlike the old session-only undo stack. The editor's `‹`/`›` step through it via a local `historyIndex`; rewinding and playing a different move truncates and replaces the tail rather than branching. Annotations aren't part of this history (they're just the face's flat current arrows/circles) — stepping back hides them rather than showing them mismatched against an earlier position.
- **Board style is a single global setting** (`storage.getBoardStyle`/`setBoardStyle`), not per-board — configured on the Settings screen, threaded down as a `boardStyle: number` prop everywhere a board renders.
- **Board orientation**: a card under a Black repertoire renders the board flipped (rank 1 top, a-file right) everywhere — editor, previews, Study. Implemented via `flipIndex(i, flipped)` in `chess.ts`, applied to grid square ordering and to every SVG arrow/circle coordinate. Never mutate `squareIndex`/`squareFromIndex` themselves — those stay in White's canonical orientation for actual game logic; flipping is purely a display-layer transform.
- **Example Repertoire**: one seeded per color group (`Repertoire.isExample: true`), built by `exampleContent.ts` by actually playing moves through the real engine (never hand-type piece maps/FEN-like state — always derive it by calling `createGameState`/`makeMove`). Sorts first in any repertoire list regardless of stored `order`. Hidden/shown via a Home-screen toggle (`storage.getExampleRepertoireHidden`) that does **not** delete it — hiding is a pure visibility filter (`getVisibleRepertoires`), never destructive. Fully editable like a normal repertoire, but its per-row "⋮" menu shows "Restore original content" instead of "Delete" (calls `restoreExampleRepertoire`, which wipes and rebuilds just that repertoire's openings/cards from `buildExampleContent`).
- **Repertoire-list auto-skip**: tapping White/Black on Home skips straight to the sole repertoire's Openings screen when there's exactly one *visible* repertoire, unless the Settings toggle "Show multiple repertoires" is on (`storage.resolveGroupEntry`). This exists because almost nobody uses more than one repertoire per side.
- **Migration**: `storage.ts`'s `migrate()` backfills fields added after data already existed (e.g. `front`/`back` on old boards, defaulting both to whatever the single old board used to be; `text`/`moves` on old faces; old card-level `front.text`/`back.text` moved onto the first board's front/back text, creating that board if the card had none) so existing local test data keeps loading without crashing. When changing the data shape, always add a backfill here rather than assuming fresh data.

## Engine (Stockfish)

The board editor (`ReactionBoardEditorOverlay.tsx`) runs a real Stockfish engine — an eval bar to the right of the board, a top-3-moves panel above it (best move blue, styled as a bordered panel matching the Description field's width), and best/2nd/3rd move arrows drawn on the board (best in a distinct blue from the user's own annotation blue, thicker). Analysis re-runs for whatever position is currently on screen, in any mode/phase, debounced 350ms.

**Why this was hard (read before touching anything engine-related):**
- **Hermes (RN's JS engine) has no WebAssembly support.** The engine can't run in React Native's own JS thread at all — it has to run inside a hidden `react-native-webview` `WebView` (a real Chromium context), bridged via plain UCI text lines over `postMessage`. `src/engine/useStockfishEngine.tsx` is that bridge; `assets/engine/index.html` is the page loaded into the WebView.
- **Android's WebView refuses to load a dedicated Worker's script from a `file://` URL** — no `allowFileAccess`-style prop fixes this, it's a hard Chromium restriction. The workaround (in `index.html`): fetch the engine JS via `XMLHttpRequest` (not `fetch()` — `fetch()` has been observed to hang forever, never resolving or rejecting, on `file:///android_asset/` URLs in this WebView; a *successful* local-file XHR reports `status 0`, not `200` — treating that as failure is a trap), wrap it in a `Blob`, and create the `Worker` from `URL.createObjectURL(blob)` instead.
- **Modern WASM NNUE Stockfish builds require WASM SIMD**, which this device's WebView compiles/instantiates fine but faults on at runtime the first time it's actually called (`RuntimeError: null function` — an indirect call through an empty function-table slot). There's no single-threaded, non-SIMD WASM NNUE build available anywhere (the one non-SIMD variant upstream offers needs multi-threading, which needs `Cross-Origin-Embedder/Opener-Policy` HTTP headers a header-less local WebView page can't have). **Current engine is `stockfish-18-asm.js`** — Stockfish 18 NNUE compiled to ASM.js (plain JavaScript, no WebAssembly at all) specifically to sidestep this. It's ~10.5MB and slower than WASM would be, but works reliably. If tempted to "upgrade" back to a WASM build, expect this exact class of failure again unless SIMD support on the target device has genuinely changed.
- **These single-threaded Stockfish.js builds crash (native-code memory fault) if a new `position`/`go` is sent while a previous search hasn't confirmed it stopped** — a documented upstream issue (search GitHub issue trackers for `nmrugg/stockfish.js` "memory access out of bounds" for the report this matches). `useStockfishEngine.tsx` works around it with a real queue: `searchingRef`/`pendingRef` track whether a search is in flight, and a new `evaluate()` call while one is running just sends `stop` and remembers the target — the actual `position`/`go` for it is only sent once the engine's `bestmove` line confirms the previous search truly ended. Do not simplify this back to "just send stop then go" — it will crash after a few quick moves.
- **`assets/engine/*.js` must be excluded from Metro** (`metro.config.js`'s `resolver.blockList`) — Metro's file watcher/dependency-graph crawler otherwise tries to walk and parse this huge, non-RN-module JS file (or previously, the .wasm binary) and crashes (`Failed to start watch mode` / internal `DependencyGraph` errors that persist even across a full cache clear). If a future engine-file swap reintroduces this class of error, check `metro.config.js` still covers the new filename pattern.
- **Bundled UCI options**: `setoption name MultiPV value 3` is sent on `uciok`. (An earlier classical, pre-NNUE engine build needed `setoption name Contempt value 0` to stop systematically inflating evals in favor of whoever was to move — that build and option are gone now that the engine is NNUE, but if evals ever look suspiciously skewed again, that's the kind of thing to suspect.)
- **Evaluation direction**: UCI `score cp`/`score mate` are relative to the side to move — the hook flips the sign so everything (eval bar, move list, arrows selection) reads left-to-right as White's perspective, like any normal chess GUI.

## UI/UX conventions (established through iteration — follow these)

- **No Unicode glyphs for icons that need to look intentional** (back arrows, pencils, gears, rewind icons) — draw them as `react-native-svg` `<Path>`s instead. Text glyphs don't center reliably across fonts/platforms. See `Common.tsx`'s `BackArrowIcon`/`EditPencilIcon`/`GearIcon` for the pattern.
- **Touch handling on interactive boards uses `PanResponder`, not `Pressable`/`onPress`**, whenever the board sits inside a `ScrollView`. `onPress` waits out a tap-vs-scroll gesture negotiation before firing, which reads as a delay between tapping and the piece/arrow responding. `PanResponder`'s `onStartShouldSetPanResponder` claims the touch immediately. See any board editor or Study screen for the `measureGrid`/`squareFromPage`/`arrowStartRef` pattern.
- **`useLayoutEffect`, not `useEffect`, for anything that must apply before paint** — e.g. `usePieceAnimation` sets up the sliding-ghost animation in `useLayoutEffect` specifically to avoid a one-frame flash where a move appears to happen instantly before snapping back and animating.
- **Never call a hook after a conditional early return** — a real bug was introduced and caught this way in `PlanStudy.tsx`. All hooks (`useState`/`useMemo`/`useEffect`/`useRef`) must run unconditionally on every render; do the `if (!thing) return <Fallback/>` bail-out only after every hook call.
- **Color language**: `colors.primary` (green) = correct/yours/constructive; `colors.danger` (red) = wrong/destructive; `colors.gold` = retry/warning/round-2 banner. Keep this consistent in any new status text or button.
- **Numbered arrows** (`NumberedArrowsSvg`/`NumberedArrowBadges` in `ChessBoard.tsx`) are the shared "which arrow is which" treatment — thin lines matching the plain `ArrowsSvg` style, badges offset to the side of the arrow (not on its midpoint) to avoid collision on short/parallel arrows, numbered only within groups of 2+ same-colored arrows.
- **Board flip**: any new board-rendering code must accept a `flipped: boolean` and apply `flipIndex` to both the square grid order and every arrow/circle coordinate — check `ReactionStudy.tsx`/`PlanStudy.tsx`/`ReactionBoardEditorOverlay.tsx` for the exact pattern before adding a new board view.
- **Drawing arrows/circles**: drag = arrow, tap (no movement) = circle, using whatever color is currently selected. Drawing the same arrow again in the same color removes it (toggle); same span, different color replaces it. This lives in each editor's `addArrow`/`toggleCircle`.

## Verification workflow (Claude has no device access)

After any change, before reporting it as done:

```bash
npx tsc --noEmit
npx expo export --platform android
rm -rf dist
```

Both must be clean. This is the *only* way to catch runtime errors without a device — `tsc` catches type errors, the export catches bundler/import errors (a real hook-ordering bug and a stale-cache "1 module" bundling failure have both been caught/discussed this way). Never claim a UI change "works" — only that it compiles and bundles; the user verifies actual behavior on their device and reports back with screenshots when something's off.
